# Anti-Loop Discipline (Дисциплина против зацикливания)

**ТРИГГЕР:** Загружать при длинных многошаговых задачах, Computer Use / автоматизации десктопа, перезапусках gateway/сервисов, и ВСЕГДА когда агент замечает, что повторяет действие или крутит одни и те же рассуждения. Также при фразе пользователя «хватит мельтешишь» / «ты зациклился».

Цель: снизить до нуля зацикливание рассуждений и действий агента. Ключевой факт из исследования (см. `references/anti_loop_research.md`): **правила в промпте/памяти — слабейший слой.** Надёжность дают механические стоп-краны в рантайме. Промпт-правило снижает вероятность; только детерминированный код приближает к 100%.

## 🛑 ПЯТЬ ПРАВИЛ (обязательные, по всей длине чата)

### 1. Fail-Fast — максимум 2 попытки на атомарную операцию
- Считается **только для failing/mutating** операций (мутация состояния, клик, запись, запуск). Повтор **read**-операции (чтение лога, GET, поиск) лимиту НЕ подчиняется.
- При двойном сбое тем же методом повтор **запрещён**. Дальше только: смена вектора (правило 2) ИЛИ вопрос пользователю. Третья слепая попытка = нарушение.

### 2. Method Swap — эскалация на надёжный системный уровень
- Если визуальный/координатный способ (Computer Use, клик по пикселю) не сработал — немедленно переключаться на более надёжный уровень:
  - горячие клавиши (например `Ctrl+,` вместо клика по кнопке настроек),
  - инъекция JS через консоль отладки,
  - прямой IPC-вызов (Electron/CDP),
  - CLI/API вместо GUI.
- Обобщение: при сбое любого способа → следующий **надёжнее**, а не «тот же, но ещё раз».
- Эскалация предпочтительнее третьей попытки того же метода.

### 3. State Delta Verification — контроль дельты состояний
- Запрещено повторять команду, если предыдущее выполнение **не изменило физическое состояние** среды.
- Каждое мутационное действие проверяется дешёвой метрикой: изменение AX-дерева, сдвиг mtime файла, смена PID, новый сокет в netstat, exit code.
- **Дельта = 0 → метод блокируется** (повтор запрещён, переход к правилу 2).
- Только для мутаций; для reads метрика не обязательна. Дешёвые метрики (PID/mtime/exit code) предпочтительнее дорогих (полное AX-дерево).

### 4. Ouroboros Filter — защита от рекурсии собственных выводов
- При чтении логов, терминала, истории окна — **фильтровать собственные предыдущие сообщения и скрипты**.
- Анализу подлежат только **новые** системные ответы, stderr, коды выхода.
- Реализовать **механически** (dedupe по `(tool, args-hash)`), а не как поведенческую инструкцию модели — модель сама себя «подкармливает» примерами своих же вызовов (self-reinforcing snowball, см. исследование).

### 5. Context Discrepancy Stop — остановка при расхождении контекста
- Если внутреннее убеждение («шлюз на порту 10259») противоречит физическому факту (`netstat` показывает 20709) — **остановить выполнение скриптов**.
- Зафиксировать Current State одним авторитетным замером (НЕ серией замеров), обновить логику до фактов среды, и только потом продолжать.

## ➕ ДОПОЛНЕНИЯ (добавлены агентом, подтверждены источниками)

### A. Global Step Budget на ход (жёсткий, в рантайме)
- Жёсткий потолок tool-calls на один ход (ориентир 40–60). Достигнут бюджет → принудительная остановка хода с отчётом, а не продолжение.

### B. Повтор без новой информации = стоп (самый надёжный детектор)
- Результат **byte-identical** предыдущему (тот же вывод, тот же hash) → стоп. Это основной no-progress guard: step-лимиты — лишь backstop, который убивает цикл ПОСЛЕ того, как бюджет сожжён; настоящий детектор — отсутствие прогресса.

### C. Checkpoint перед fan-out
- Перед параллельным разветвлением — execution checkpoint с полем `information_gained`. Два подряд false → инъекция «объясни результат или объяви недосягаемым»; три подряд → принудительное завершение sub-goal.

### D. Цикл мышления ≠ цикл действий
- Отдельный детектор: одинаковые рассуждения без нового действия — это тоже зацикливание (overthinking), даже если tool-calls разные.

### E. Форма эскалации (обязательный шаблон вопроса пользователю)
```
BLOCKED
Tried: <что пробовал, методы>
Believes: <гипотеза причины>
Question: <ОДИН конкретный вопрос>
Default: <что сделаю, если ответа нет>
```

## 🏗️ ТРЁХСЛОЙНАЯ МОДЕЛЬ ПРИНУЖДЕНИЯ
1. **Промпт/Память** (слабый) — правила как факты в MEMORY + этот skill. Снижают вероятность, не гарантируют.
2. **Skill** (средний) — процедурная дисциплина, загружается при высоком риске (Computer Use, gateway, длинные bash).
3. **Рантайм-гардрейлы** (сильный, единственный близкий к 100%) — hard step-budget, dedupe `(tool,args)` со стопом, auto-signal при нулевой дельте, неуязвимый tool-call ledger (tool, args-hash, terminal flag) в зоне контекста, которую суммаризация не трогает.

### Статус рантайм-слоя (Hermes, проверено 01.09.2026)
Включено в `config.yaml` → `tool_loop_guardrails`:
- `hard_stop_enabled: true`
- `warn_after`: exact_failure=2, same_tool_failure=3, idempotent_no_progress=2
- `hard_stop_after`: exact_failure=2, same_tool_failure=4, idempotent_no_progress=3
- `agent.max_turns: 200` (bridge → HERMES_MAX_ITERATIONS; .env чистый, без ghost)

Механизмы в `agent/tool_guardrails.py`:
- `ToolCallGuardrailController.before_call()` — блок ДО выполнения при count ≥ cap (Fail-Fast = 2).
- `after_call()` — подсчёт exact/same-tool failures, halt на пороге.
- `observe_call()` / stall guards — notice на 3-м идентичном вызове + result stubbing (byte-identical duplicate → reference stub, экономия токенов).
- Per-turn loop caps (web_searches, subagents) — жёсткий потолок на ход.

**АКТУАЛЬНЫЙ КОНФИГ (проверено 04.09.2026, бэкап `config.yaml.bak_maxturns_20260903_234858`):**
- `agent.max_turns: 400` (ранее 200).
- Guardrails = **warn-only** для интерактивных сессий: warn exact=2 / same=4 / noprog=3; явный hard_stop из конфига УБРАН.
- Hard-stop остаётся только через auto-cron (те же пороги). То есть в живой сессии `[hermes note: Nth consecutive identical call]` — это ПРЕДУПРЕЖДЕНИЕ, а не стоп-кран; единственный жёсткий предел — max_turns (и он большой).
- **Вывод:** поведенческий слой (этот skill) несёт основную нагрузку против зацикливания; рантайм-блок на идентичные вызовы в интерактиве НЕ срабатывает.
- Проводка: `agent_init.py` загружает конфиг в `ToolCallGuardrailController`; `tool_executor.py:675` вызывает `before_call()` ДО каждого инструмента (sequential+concurrent); `run_agent.py:9019–9039` — `after_call()` → guidance/halt; `conversation_loop.py:8084` — halt завершает ход (`_turn_exit_reason="guardrail_halt"`).
- Тесты: `tests/agent/test_stall_guards.py` + `tests/run_agent/test_tool_call_guardrail_runtime.py` + `tests/tools/test_delegate.py` = 128 passed / 1 pre-existing Windows-only fail (path normalization in relay rewrite test, не связан с guardrails).
- **Py3.14 баг:** `tools/daemon_pool.py` читал `self._initializer`/`self._initargs` — атрибуты перенесены в `WorkerContext` в 3.14. Патч с fallback'ом на оба API добавлен. Живой рантайм (C:\Python314) не был затронут, но код теперь версионно-независим.

Dropped-tool-call recovery (`conversation_loop.py`): finish_reason="tool_calls" с пустым массивом → nudge «issue the actual tool call now» + до 3 retry. Пустой reasoning-only ответ → `_CODEX_INCOMPLETE_NUDGE`. Это закрывает Qwen-баг «пустой tool call → задача готова».

## 🚨 RECOVERY PROTOCOL — когда цикл УЖЕ идёт

Если агент обнаружил, что уже повторяет идентичный tool-call (или получил `[hermes note: Nth consecutive identical call]`):

1. **НЕ повторять вызов ещё раз** — даже «с другим аргументом», если результат уже известен.
2. **Остановиться и переформулировать задачу:**
   - Что я пытаюсь узнать?
   - Есть ли у меня уже ответ из предыдущих результатов?
   - Если да → использовать имеющиеся данные, перейти к следующему шагу.
   - Если нет → сменить ВЕКТОР (другой инструмент, другой подход), а не повторить тот же.
3. **Зафиксировать в контексте:** «Цикл на [tool+args], остановлен на N-м повторе. Данные уже собраны / нужен новый вектор.»
4. **Продолжить работу** — не завершать сессию, не спрашивать пользователя (если задача решаема без него).

### Практический кейс (04.09.2026): 300+ повторений terminal-parse — ПОВЕДЕНЧЕСКИЙ СЛОЙ НЕ СПРАВИЛСЯ
Ночная автономная задача (аудит пайплайна WhatsApp→ТГ). Агент ~300 раз подряд шёл одним и тем же `terminal python -c "..."` (парсинг сегмента лога `notify_relay.log`, сопоставление RECV #N ↔ ⏰-таймстампов), каждый раз получая byte-identical результат (`unknown count: 54, max# unknown: 98`) и игнорируя `[hermes note: Nth consecutive identical call]` вплоть до N≈316. Задача была убита только потолком max_turns. Три системных фактора:
1. **Warn-only guardrails** — рантайм лишь предупреждал, не блокировал (см. статус конфига выше).
2. **Compaction handoff** — после суммаризации «застрявшая» подзадача (RECV↔⏰ correlation) вернулась как active request; модель восприняла её как незавершённую и «доделывала» тем же инструментом.
3. **Одна подзадача съела весь бюджет** — пункты 2–4 ночной задачи так и не начались.

**Уроки (обязательные):**
- `[hermes note: Nth consecutive identical call]` при N ≥ 3 — это ПРИКАЗ немедленно сменить вектор или закрыть подзадачу, даже если guardrail помечен warn-only. Повтор после N≥3 = нарушение независимо от типа операции (read или mutating).
- **Budget-per-subtask:** в длинных multi-part задачах (ночные задания, аудиты из N пунктов) выделяй мысленный лимит ~15–20 tool-calls НА ПОДЗАДАЧУ. Достигнут → фиксируешь частичный результат и ИДЁШЬ к следующему пункту. Одна подзадача никогда не должна пожирать весь ход.
- **Handoff-aware stop:** если compacted summary описывает застрявший шаг («stuck point», «parsing loop»), НЕ продолжай его тем же методом — это именно то, что уже не дало результата. Либо новый метод (другой формат парсинга, другой источник данных), либо явное объявление шага недосягаемым и переход дальше.
- **Не усложняй парсер бесконечно:** если один regex/скрипт парсинга не сходится 3 раза — меняй подход целиком (читай сырые строки вручную, используй sqlite вместо лога, упрощай до минимального вопроса), а не вариации одного скрипта.
- **Одинаковый вывод = стоп, даже при exit 0:** «exit 0 + N строк вывода» НЕ означает успех. Если результат byte-identical предыдущему вызову (тот же текст, те же значения) — это отсутствие прогресса независимо от exit code. В кейсе 04.09 каждый из ~300 вызовов возвращал `exit 0` и 3 строки (`unknown count: 54...`) — формально «успех», фактически ноль информации. Проверка: сравнивывай ТЕКУЩИЙ вывод с предыдущим ДО следующего вызова; идентично → стоп.

### Практический кейс (03.09.2026): inspect.getsource loop
Агент 10+ раз подряд вызывал `execute_code` с `inspect.getsource(concurrent.futures.thread._worker)` / `_WorkItem` на Python 3.14, каждый раз получая обрезанный вывод (2500 chars) и не извлекая новых данных. Триггеры остановки:
- Результат byte-identical (тот же источник, та же обрезка) → правило B сработало бы при наличии runtime dedupe.
- **Корневая причина:** модель пыталась «понять» internals CPython для диагностики тестового фейла, но реальный путь решения (патч `daemon_pool.py` с fallback'ом) не требовал полного понимания stdlib-интерфейса. Эскалация должна была быть: «мне не нужен полный source — мне нужен working patch» → прямой патч + живой тест, а не инспекция.
- **Урок:** при диагностике версии-API — достаточно проверить `hasattr(obj, 'method')` или signature, а не читать весь `inspect.getsource`. Один точечный probe > десять полных выгрузок.

### Практический кейс: верификационный цикл после компакции (нормативные акты)
После компакции handoff-суммари перечислил незакрытые пункты «верифицируй норму X»; агент потратил 10+ web_search/web_extract на повторную верификацию норм, уже верифицированных ранними раундами сессии — каждый запрос с чуть иной формулировкой, каждый результат «подтвердил», пользователь прервал: «зациклился».
- **Детектор — семантический, не byte-identical:** повторная верификация факта, уже подтверждённого первоисточником, = нулевой прогресс, даже если текст запроса отличается (тот же факт + тот же класс источников). Правило B (byte-identical) этот случай пропускает.
- **Pin-then-synthesize:** верифицированные факты (норма, срок, размер санкции, реквизиты документов) сразу пишутся в рабочий файл (расчёт/записка), и дальнейшие раунды цитируют файл, а не живой поиск. Факт, уже закреплённый в файле, — закрыт.
- **Отличие от handoff-aware stop:** там шаг был застрявшим (нет результата); здесь шаг завершён (результат есть), цикл — повторный прогон завершённой фазы.
- **После «зациклился/хватит» — смена класса вызова обязательна:** следующий ход ассистента НЕ содержит вызовов того же класса (доп. поиски/extract) и сразу переходит к синтезу (черновик/отчёт) на уже собранных данных. Доп. поиск в ответ на стоп-сигнал = повторное нарушение.

### Конкретные триггеры для немедленной остановки:
- `[hermes note: Nth consecutive identical call]` при N ≥ 3 → стоп, переосмыслить.
- Результат byte-identical предыдущему → стоп (правило B).
- Три подряд read-операции с тем же ожидаемым результатом → стоп, использовать первый результат.
- Верификация факта, уже закреплённого в рабочем файле (расчёт/записка) → повторный поиск запрещён, цитируем файл (семантический дубль).
- Пользователь сказал «зациклился» → вызовы того же класса (поиск/extract) запрещены, немедленный переход к синтезу.

## ⚠️ PITFALLS
- **Lossy summarization ПОВТОРЯЕТ циклы:** суммаризатор выбрасывает факт «этот tool уже вызывали», модель пере-выводит то же действие. Дurable fix — компактный tool-call ledger вне зоны суммаризации.
- **Qwen-класс моделей (в т.ч. рабочая Qwen3.8-27B)** склонен к collapse в repeated identical tool_call внутри окна: модель пишет «let me stop this loop» но шлёт тот же вызов — нет client-side circuit breaker. Именно поэтому рантайм-слой обязателен.
- Не путать read-повторы с violating: повтор чтения не нарушает Fail-Fast; нарушение — повтор мутирующего действия без дельты.
- Не гнаться за «100% через промпт» — это недостижимо; честная цель = рантайм-стоп-краны + политика как снижение вероятности.
- **skill_manage create на существующий skill** → ошибка «already exists». Сначала `skill_view(name)` для проверки, затем `patch` (не `create`). При создании нового skill description обязан быть ≤60 символов (бюджет system-prompt); детали — в body.
- **tool_search regex с `/` или `(`** → rg parse error. Использовать `{0,N}` вместо групп, экранировать спецсимволы.
